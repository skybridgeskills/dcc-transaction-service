# OID4VP 1.0 verifier binding: unsigned `redirect_uri` + `direct_post`

- Status: Accepted
- Date: 2026-07-11
- Workflow: `verify`

## Context

The `verify` workflow accepts wallet presentations over
[OpenID for Verifiable Presentations 1.0](https://openid.net/specs/openid-4-verifiable-presentations-1_0.html)
alongside the VC-API / VPR / CHAPI paths, targeting the OID4-ECDSA interop
profile (Data Integrity credentials, `did:key` holders, `ecdsa-rdfc-2019` /
`eddsa-rdfc-2022`).

OID4VP 1.0 offers several axes of choice, each with a heavier and a
lighter option:

- **Query language:** DCQL (1.0-native) vs `presentation_definition` /
  PEX (pre-1.0).
- **Client identification / request integrity:** a signed request object
  under the `did:` / `x509_*` client_id schemes vs the unsigned
  `redirect_uri` prefix (§5.9.3).
- **Response delivery:** `direct_post` vs `direct_post.jwt` (encrypted /
  JARM).

The service holds **no asymmetric signing keys of its own** (VC signing is
delegated to an external signing service; the only local JWT infra is HS256),
so a signed request object on this binding would mean net-new infrastructure.
The `verifier-core` pipeline already verifies Data Integrity proofs (ECDSA +
EdDSA, `did:key` + `did:web`) and runs the async Open Badges pass.

## Decision

The verifier side of OID4VP 1.0 is a **binding on the existing `verify`
exchange**, taking the lighter option on the delivery and client-identification
axes and both options on the query-language axis:

1. **Both query languages, selected per exchange, with DCQL as the default.**
   `variables.oid4vpQueryLanguage` picks one; an exchange that says nothing
   gets DCQL. Both sides of the wire are covered: the authorization request
   emits either `dcql_query` or `presentation_definition` (embedded by value),
   and the `direct_post` handler parses either a DCQL `vp_token` object or a
   PEX `vp_token` plus `presentation_submission`.

   Either query is derived from the exchange's existing configuration. For
   DCQL, `meta.type_values` is the **constant** VCDM `VerifiableCredential`
   IRI (per §B.1.1, `type_values` are fully-expanded IRIs) and `claims` map 1:1
   from `vprClaims`. Specific credential-type / `@context` / trusted-issuer
   enforcement stays post-verification, exactly as on the VC-API path.

   ⚠️ **Why not DCQL alone**, which is what the lighter option on this axis
   would have been. Two reasons, and the first is structural:

   - The reference holder in the interoperability test suite speaks
     Presentation Exchange only. A DCQL-only verifier therefore **cannot
     self-test the OID4VP present leg at all** — the leg can only be marked
     untestable, and no amount of effort on this side closes that.
   - Speaking both makes it possible to ask a client the **same question
     twice** and compare the answers. That is how a client that honours a
     `type` constraint while ignoring a `format` constraint is caught: it
     offers its holder a credential the verifier's own definition would
     reject, and the defect is invisible unless the two constraints can be
     varied independently.

   ⚠️ **The two builders are kept equivalent, and a test enforces it.**
   `dcql.ts` and `pex.ts` consume the same `vprClaims` and address the same
   nodes; a test asserts the claim mappings match. If they drift, comparing a
   client's behaviour across the two languages becomes meaningless, which
   would destroy the reason for speaking both.

   ⚠️ **The response handler discriminates on the exchange, never on the
   payload.** It branches on the language the exchange *asked in*. Sniffing
   the response shape would turn a malformed answer into a silent fallback
   down the other code path — precisely the accommodation that hides a defect
   this service exists to reveal. A response in the wrong shape is reported as
   a failure.

2. **Unsigned request with the `redirect_uri` client_id prefix.**
   `client_id = redirect_uri:<response_uri>`; all verifier metadata
   travels inline in `client_metadata`. The request is served as unsigned
   JSON at a `request_uri` (by reference, keeping the QR small). No
   asymmetric signing infrastructure is introduced.

3. **`direct_post`** with `response_type=vp_token`. The wallet POSTs the
   `vp_token` to the `response_uri` — an object keyed by credential-query id
   on the DCQL arm, a `vp_token` plus `presentation_submission` on the PEX
   one.

4. **New unauthenticated per-exchange endpoints**
   (`GET .../openid4vp/request`, `POST .../openid4vp/response`), mirroring
   the OID4VCI no-auth-middleware pattern. Security is bound to the
   unguessable exchange id plus a single-use `state` (minted lazily, one
   response accepted) and the exchange `challenge` reused as the OID4VP
   `nonce`. Because `verifier-core` does not enforce the VP proof
   `domain`, the response handler enforces `domain === client_id` itself;
   `nonce` is verified cryptographically by the pipeline.

5. **Reuse the existing verify pipeline** (`preparePresentationForVerify`
   → `participateInVerifyExchange`) unchanged — the extracted VP is fed in
   as `data`, so the exchange finalizes to `complete` / `invalid` /
   `active`(async OB) identically to the VC-API path.

## Consequences

- **No new signing infra**; the binding ships as a self-contained
  `src/oid4vp/` module plus two Hono routes and a `getProtocols` entry,
  with all OID4VP runtime state inline under `variables.oid4vp`.
- **Interop contract is unsigned + `direct_post`.** A counterpart wallet must
  support `direct_post` and one of the two query languages.
- **Trust is transport-scoped.** With the `redirect_uri` prefix the wallet
  cannot cryptographically authenticate the verifier; trust rests on TLS +
  the unguessable exchange URL. A deployment needing verifier authentication
  needs the signed request object, which is a separate decision —
  [ADR 2026-08-25](2026-08-25-oid4vp-request-object-envelopes.md) §6.
- **Two query languages is two code paths to keep in step**, and the
  equivalence test is what keeps them there. Adding a `vprClaims` feature
  means adding it in both builders or failing that test.
- **Out of scope for this binding:** `direct_post.jwt` (encrypted / JARM
  responses), `presentation_definition_uri` (by-reference definitions are a
  second delivery mode and add a route; deferred until a client requires it),
  and the (non-existent in OID4VP 1.0) "authorization code flow".
- **General JSONPath evaluation is deliberately not implemented.**
  `descriptor_map` path resolution supports `$`, `$[n]` and dotted/bracketed
  member access only. A full JSONPath evaluator is a dependency and an attack
  surface this service does not need; a path outside that set is reported
  verbatim as a finding rather than accommodated.

## Alternatives considered

- **A signed request object on this binding** (`did:` / `x509_*` client_id
  schemes). Rejected here: it requires asymmetric signing this binding does
  not have, for a trust benefit its interop target does not require. It is
  a different envelope under a different client_id prefix, decided in
  [ADR 2026-08-25](2026-08-25-oid4vp-request-object-envelopes.md) §6.
- **One query language only.** Rejected: whichever one is picked, the
  verifier loses either self-testability against the reference holder or the
  ability to vary one constraint at a time — see decision 1.
- **Sniffing the response shape** to decide which query language a `vp_token`
  answers in. Rejected with decision 1: it makes a malformed response
  indistinguishable from a well-formed one in the other language.
- **A standalone verifier workflow** rather than a binding on `verify`.
  Rejected: the credential-type config, trusted-issuer/registry checks,
  claims validation, and async OB pass already live on `verify`; a binding
  reuses all of it and keeps a single result surface for polling clients.
